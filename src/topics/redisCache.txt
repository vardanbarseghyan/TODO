1) Yes, exactly right on both points!
Each user gets their own separate cache entry in Redis.
The key = "#user.id" is a SpEL expression (Spring Expression Language).
The # symbol tells Spring: "this is not a literal string — go find the actual value of user.id at runtime."
So when Vardan (with ID 550e8400-...) calls getAllCategories, Spring evaluates #user.id to 550e8400-... and the Redis key becomes user_categories::550e8400-....
When another user (with ID 8d314ce5-...) calls the same method,
the Redis key becomes user_categories::8d314ce5-....
So Redis ends up storing something like:
user_categories::550e8400-e29b-41d4-...  →  [Vardan's categories JSON]
user_categories::8d314ce5-5840-4e65-...  →  [Other user's categories JSON]
Completely separate entries. When Vardan creates a new category, @CacheEvict(key = "#user.id") deletes ONLY user_categories::550e8400-... — the other user's cache is untouched.
This is exactly what you want — one user's actions should never affect another user's cached data.

//First call (writing to Redis): Your method returns a Page<CategoryResponse> which is actually a PageImpl object. Redis takes this object, Jackson converts it to a JSON string like {"content": [...], "number": 0, "size": 10, "totalElements": 3, ...}, and stores that JSON string in Redis. This works perfectly because Jackson knows how to read an object's fields and write them as JSON.
  Second call (reading from Redis): Spring finds the cached JSON string in Redis and asks Jackson: "Please convert this JSON back into a Java object." Jackson looks at the JSON and sees it needs to create a PageImpl instance. To create any Java object, Jackson needs one of two things — either a default constructor (no arguments) or a constructor annotated with @JsonCreator that tells Jackson which JSON fields map to which constructor parameters.
  The problem is that PageImpl is a Spring class that you don't control. It has no default constructor — its constructor requires List content, Pageable pageable, and long total. Jackson sees this and says: "I have JSON fields like content, number, size, totalElements, but I don't know how to map these into PageImpl's constructor parameters. I give up." That's the error you saw.
  Your RestPage class solves this by extending PageImpl and adding a constructor with @JsonCreator and @JsonProperty. Now Jackson sees the JSON, finds the @JsonCreator constructor, matches "content" → content, "number" → number, "size" → size, "totalElements" → totalElements, and successfully creates the object.
  So the core issue is: Jackson can convert Java → JSON easily (just read the fields), but JSON → Java is harder because it needs to know HOW to construct the object. Your custom classes have @NoArgsConstructor from Lombok so they work fine. Spring's PageImpl doesn't, so we needed the RestPage wrapper.


  Page is an interface — it defines what methods must exist (like getContent(), getTotalElements(), getTotalPages(), getNumber()) but has no actual code inside. It's like a contract that says "any class implementing me must have these methods."
  PageImpl is a class that implements the Page interface. It contains the actual code — the real fields (content list, total elements, pageable info) and the real method bodies that return values. When your repository returns Page<Todo>, the actual object in memory is a PageImpl<Todo> — it's just referenced through the Page interface.
  Think of it like this from your C# experience: Page is like an interface IPage, and PageImpl is the concrete class that implements it. Same concept.
  Your RestPage extends PageImpl which implements Page. So the hierarchy is:
  Page (interface)
    ↑ implements
  PageImpl (class)
    ↑ extends
  RestPage (your class)
